# M11 编排层（0.9.0）实施报告

- 计划：`子计划书-子智能体编排.md` v1.0 定稿（2026-11-25，D41–D47）

## 为什么改

0.8.x 的单会话工具面是「worker 的超集里砍掉动手工具」，仍有两个结构性问题：

1. `subagent` 工具一次只能派一个，没有并发上限；宿主 `maxActiveSubagents` 默认 8，超出直接抛 `ACTIVATION_LIMIT_REACHED`，插件没有承接。
2. 派出去的子智能体用完即扔，下次同类任务要从头读同一批文件（实测 12 个真实子会话里 `client.js` 被读 11 次、`package.json` 10 次），并留下大量 `ev=26/tools=0` 的回声会话。

## 0.9.4 修复（2026-11-25 23:50 用户报「一堆子智能体还没收」）

现象：用户截图 13 个来自「基地」单会话的子智能体一直挂着；`/status` 里 `tickets=0`，`state.json` 有 `singleSessionChildUnknown` 31 条，`single-session.log` 15:44 起每轮都刷 `child <id>: 读不到事件，先不动（第 N 次）`。

根因（读宿主源码 `@deepseek-ai/dsh-api-session-controller/lib/index.js:1246` 的 `validateAddress` 确认）：宿主对 `origin === 'subagent'` 的会话只接受 **subagent 地址**，用 `{kind:'session'}` 读会抛 `session/agent-busy`「subagent Sessions require their durable parent address」。旧代码 `readEvents` 只拼 session 地址，又 `catch { records = [] }` 把异常吞成空数组 → 每个子会话都判 `unknown`，既不纳管也不归档。0.9.1 的「不归档」和 0.9.3 的「退避重试」都是对的，只是永远读不到。

修复：

1. `lib/single-session.js` 新增 `childAddressOf(child)`（`{kind:'subagent', parentSessionId, childSessionId, mode:'unknown'}`）与 `api.readChildEvents`；`reconcileChildren` 改用它，读失败时打日志（带 `error.code`）再按 unknown 退避，不再静默。`mode` 传 `unknown` 让宿主按 descriptor 判定，避免 one-shot/continuable 记错。
2. 标题风暴（同批修复）：宿主 `list()` 的 summary 顶层没有 `title`，标题在 `projections.values.title`（可能是 `{val}` 投影项）。旧代码只读 `summary.title` → 每轮都判「标题不一致」→ 每 60s rename 一次。现加 `sessionTitleOf()` / `normalizeTitleText()`（对齐宿主 cleanTitleText：去控制符/零宽、折叠空白、80 字节截断）+ 5s 观察窗口 + 1min/5min/30min 退避，对账一致即清记录。

测试：新增 3 条（`childAddressOf` 地址形状、读失败进 unknown 不归档、纳管子会话时带父会话身份），连同标题退避用例 → **185 pass / 0 fail**。版本 0.9.4。

## 0.9.7 修复（2026-11-26 09:10 用户报「一点击单会话好像就自动归档了」）

现场先核事实：宿主跑的是 0.9.6（进程 21644，08:56 启动），三条登记（插件/基地/基地电脑镜像）都在、都没进 `archivedSessionIds`；`single-session.log` 里「compact failed … 没有挂 compaction 服务」最后一条停在重启前 47 秒，重启后 0 条。也就是说：**会话本身没被归档**，但归档面确实有两个问题：

1. **归档不幂等**：`listSessions()` 会连已归档的子会话一起返回，`archiveChildSession` 只按「还在列表里 + 空闲」选目标，于是每分钟对同一批 17 个 noise 子会话重复 `archiveSession`，日志刷 `archived child …` / `purged stale workers: 763/763`。
   - 修：`lib/child-archive.js` 增 `state.singleSessionChildArchived`，归档成功的 id 记下来，下次直接返回 `true`，不再打宿主、不再刷日志。
2. **带 `stopActivity` 的归档绕过登记保护**：D26 的「登记后禁止入档」只靠 `workspace/session-activity` 上报活动拦截；侧栏「停止并归档」走 `stopActivity: true`，活动检查被跳过 → 已登记的单会话可以被归档掉（用户看到的就是「点一下会话就被归档」这一类）。
   - 修：`lib/single-session.js` 增 `onArchived(request)`（`workspace/session-archived` 事件，宿主在 durable 归档后派发）；已登记且不是控制台「解除单会话」中的会话立刻 `unarchiveSession()` 拉回来，日志 `archived registered session restored: …`；`lib/index.js` 订阅该事件。

测试：新增 2 条（`onArchived` 的恢复/忽略/失败三分支、归档幂等只打一次宿主）→ **240 pass / 0 fail**（含 2 条 todo）。版本 0.9.7。

## 0.9.10 修复（2026-11-26）：维护不再强行 resume 冷会话，侧栏那一行不再消失

- 现场（0.9.9 埋点）：`single-session.log` 在每次维护压缩时都有
  `trace created <id>` → 15ms 后 `trace DISPOSED <id>`，紧接着 `compact failed <id>: 会话不在宿主里（可能已关闭），无法压缩`。
  手动 `POST /action {"action":"compact"}` 能稳定复现同一对事件。
- 根因：`compactOne()` 在会话是冷的时候（宿主 `ctx.agents` 里没有 agent）为了压缩去 `api.resolveAgent(sessionId)` 强行 resume。
  宿主内部会先 `sessionQuery.observeSession` 把会话 prepare 成对象（`session/created`），resume 失败后释放观察权（`session/disposed`）；
  `dsh-api-session-controller/src/index.ts:229` 把 `session/disposed` 翻成 `api-session/removed`，
  客户端 `manager.ts:686 handleSessionRemoved` 对非子智能体直接 `{kind:'remove'}` 删掉那一行 → 用户看到「点一下/维护一轮，单会话就从侧栏消失」，
  再点控制台「会话」时 `sessions.retain` 报 `unknown session`。
- 修复（不再自愈、不再重试，直接不做会引发副作用的事）：
  - `compactOne(view, reason)`：只用 `view.agent`（`inspect` 里 `ctx.agents.get` 的被动结果）；没有 agent 就 `return { skipped: true, reason: 'cold' }`，**绝不 resolveAgent**。
  - `compactSession(sessionId, …)`（角色压缩入口）同样改为 `api.getAgent` 被动读取，冷会话直接 `{ skipped: true, reason: 'cold' }`。
  - 附带效果：手动「立即压缩」对冷会话返回 skipped/cold（没有 agent 时压缩本来也压不了），不再制造 removed 事件。
- 测试：`test/unit/single-session.test.js` 新增 2 条——冷会话 maintain 不调 `resolveAgent`、`compactSession` 返回 `{skipped:true,reason:'cold'}`
  （harness 的 `resolveAgent` 现在会计数）→ **246 tests / 244 pass / 0 fail / 2 todo**。版本 0.9.10。

## 0.9.11 修复（2026-11-26）：compaction 桥不再卡住 dispatcher preset 挂载

- 现象：用户先在控制台删掉三个单会话，之后在任意空白会话点亮「超级智能体」图标，**按钮像没反应**；`/status` 的 `lastError` 是 `single-session: preset 未恢复（…: not-live）`。同一时段已登记的会话在侧栏仍会消失，控制台点「会话」报 `sessions.retain: unknown session …`。
- 日志证据（`logs/single-session.log`，UTC）：
  `trace CALL pin <新会话>` → `trace CALL selectPreset <新会话>` → `trace CALL unpin <新会话>` → `preset switch failed <新会话>: compaction-bridge (dsh-superagent-yh/compaction-bridge): waiting for compaction`；09:57 换一个会话重试，同样失败两次。把 `singleSession.enabled` 临时关掉后，`trace created/DISPOSED` 立刻停止——两者强相关。
- 根因：`lib/compaction-bridge.js` 顶部 `export const inject = ['compaction']`。isolate 组里的 compaction 服务要等 `compaction-basic` 把自己的 `llm/tokenMeter/sessions` 注入完才出现；宿主编排 preset 时把「插件在等服务」判成挂载失败。于是：
  - 登记时 `selectPreset` 抛错 → 回滚 unpin → 看上去「按钮失效」；
  - 已登记会话被 resume 时 preset setup 抛错 → agent 创建后立刻 dispose → `session/disposed` → `api-session/removed` → 客户端 `handleSessionRemoved` 删行、`sessions.retain` 报 unknown。
  0.9.10 只修掉了维护器主动 resume，所以「消失」换了个入口继续发生。
